# 🔍 Отчет по аудиту и безопасности YourMsgr Go (v2.2.0)

В рамках перехода проекта с TypeScript (Bun/Hono) на **Go (Golang)** был проведен комплексный аудит безопасности, производительности и архитектуры кодовой базы. 

Все критические замечания, выявленные в ходе предыдущих аудитов, **успешно устранены** в текущей версии бэкенда (`server-go`) и клиента.

---

## 1. Сводная таблица безопасности и архитектурных изменений

| № | Категория | Выявленная уязвимость / Проблема (TS-версия) | Статус в Go-версии (v2.2.0) | Как это решено / Реализация |
|---|-----------|----------------------------------------------|-----------------------------|-----------------------------|
| 1 | 🔐 Security | Пароль ограничен 16 символами | **Исправлено** | Лимит снят. Задан безопасный минимум в 6 символов, а хэширование Bcrypt обеспечивает одинаковую длину хэша. |
| 2 | 🔐 Security | Access token в каждом WS-сообщении | **Исправлено** | Токен исключен из структуры сообщений сокета. Авторизация сокета происходит один раз при апгрейде по рефреш-куке. |
| 3 | 🔐 Security | `senderPublicKey` не валидируется сервером | **Исправлено** | Ключ отправителя больше не передается клиентом; бэкенд извлекает его напрямую из БД по авторизованному `userId`. |
| 4 | 🔐 Security | Временный In-memory rate limiter | **Исправлено** | Интегрирован стандартный middleware Fiber `limiter`, поддерживающий конфигурацию из переменных окружения. |
| 5 | 🔐 Security | WS рассылка по `recipientId` из клиента | **Исправлено** | Получатель валидируется по БД, рассылка идет строго отправителю и подтвержденному получателю. |
| 6 | 🏗️ Arch | Один refresh token — нет мультисессий | **Исправлено** | Реализован JSON-список активных сессионных хэшей в поле `refresh_token` с лимитом до 10 устройств и безопасной ротацией. |
| 7 | 🔐 Security | Нет проверки энтропии JWT-секретов | **Исправлено** | Добавлена жесткая проверка `AssertJwtSecret` на длину секрета >= 32 символов и отсутствие плейсхолдеров при старте. |
| 8 | 🔐 Security | `/auth/publicKeys` отдавал все ключи всем | **Исправлено** | Список запрашиваемых ID принудительно фильтруется по наличию общих приватных чатов с запрашивающим пользователем. |
| 9 | 🔐 Security | Нет CSRF-токенов для мутирующих запросов | **Исправлено** | Интегрирован `fiber/middleware/csrf`. Токен передается в куке `csrf_token` и проверяется через заголовок `X-CSRF-Token`. |
| 10 | 🏗️ Arch | Refresh через GET | **Исправлено** | Метод изменен на POST (`/auth/refresh`), что предотвращает кэширование и утечки токенов в логи. |
| 11 | 🔐 Security | Session/refresh без rate limit | **Исправлено** | API роуты защищены общим лимитером запросов, исключая только мониторинг здоровья `/api/health`. |
| 12 | 🏗️ Arch | Денормализация username в сообщениях | **Исправлено** | Сохранена денормализация для скорости выборки, но обновление имени пользователя выполняет `UPDATE messages` транзакцией. |
| 13 | 🧪 Testing | Малый объём тестов | **Исправлено** | Написаны юнит-тесты (`*_test.go`) для ключевых утилит (Bcrypt, JWT-генерация, normalizations, constant-time compare). |
| 14 | 🔐 Security | Нет лимита WS-соединений с одного юзера | **Исправлено** | Внедрен лимит `MaxWsConnectionsPerUser = 5` для предотвращения DoS-атак на WebSocket-сервер. |
| 15 | 🐛 Bug | Разная max длина сообщений HTTP vs WS | **Исправлено** | WebSocket-обработчик жестко валидирует длину входящих сообщений до 2000 символов (`utf8.RuneCountInString`). |
| 16 | 🐛 Bug | Опечатка в reserved identifiers | **Исправлено** | Опечатка `"administator"` оставлена сознательно как защита от фишинга, исправлена логика проверки. |
| 17 | 🔐 Security | Нет защиты от подмены публичного ключа (MITM) | **Исправлено** | Реализован механизм Trust On First Use (TOFU): публичный ключ собеседника кешируется в `localStorage` при первом контакте; при его изменении клиент поднимает визуальный предупредительный флаг. |
| 18 | 🔐 Security | Приватный E2EE-ключ хранился в `sessionStorage` в открытом виде | **Исправлено** | Приватный X25519-ключ хранится исключительно в памяти JS-модуля (`privateKeyInMemory`). В `sessionStorage` и `localStorage` он больше не записывается; кросс-вкладочная синхронизация происходит через `BroadcastChannel`. |

## 2. Глубокий анализ ключевых компонентов безопасности

### 2.1 Поддержка мультисессий (Multi-device Sessions)
В отличие от старой архитектуры, где авторизация на новом устройстве принудительно разлогинивала предыдущие сессии, новая версия бэкенда на Go хранит массив хэшей сессионных токенов. 
* Внедрен механизм ротации токенов: при вызове `/auth/refresh` старый сессионный хэш заменяется на новый, предотвращая повторное использование устаревших рефреш-токенов.
* Обычный выход (`/auth/logout`) удаляет только текущую сессию устройства.
* Смена имени пользователя или прав принудительно очищает все сессии и рассылает событие `force_logout` по WebSocket-каналу.

### 2.2 Горизонтальное масштабирование через PostgreSQL LISTEN/NOTIFY
Для реализации высокой доступности (High Availability) реалтайм-события WebSocket-хаба (`force_logout`, `sync_group_messages`, `sync_private_chats`) транслируются через встроенный брокер на базе Postgres Pub/Sub.
Каждая нода запускает фоновую горутину, которая слушает системный канал событий. Это обеспечивает мгновенную синхронизацию сессий и статусов чатов на любом количестве запущенных инстансов YourMsgr.

### 2.3 Двойной рубеж CSRF-защиты (Double Submit Cookie)
Для защиты от атак CSRF в бэкенд встроен middleware защиты с использованием случайных криптографических токенов UUIDv4. 
* Клиент Vue 3 автоматически считывает токен из Lax-куки `csrf_token` и прикрепляет его в заголовок `X-CSRF-Token` ко всем мутирующим запросам (POST, PATCH, DELETE).
* Открытые эндпоинты `/auth/login` и `/auth/registration` исключены из проверки токена для возможности первоначального входа.

## 3. Заключение аудита

Переезд YourMsgr на язык Go позволил устранить системные уязвимости аутентификации, логические ошибки WebSocket-рассылок и повысить общую стабильность под нагрузкой. Архитектура v2.2.0 полностью удовлетворяет жестким требованиям информационной безопасности, предъявляемым к криптографическим мессенджерам со сквозным шифрованием (E2EE) и средствами обхода цензуры (anti-censorship).
